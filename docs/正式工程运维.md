# 服务端运行与更新

唯一工程 `D:\github\AiServer`。本文件集中维护启动、账号、诊断、配置、备份与5080交付；对接见[公共协议](../contracts/api/v1/README.md)，验证边界见[项目进度](项目进度.md)。

## 0.11.1 指定Strata存储盘

停服并备份，将0.11.1程序包的`payload`合并覆盖原工程；无需移动工程、数据库或账号／key。两个安装入口新增`--storage-root`，指定本机SSD上的绝对目录。它同时保存下载缓存、两款原始权重、Qwen MTP源数据、派生pack及引擎／源码／隔离依赖，pip缓存也跟随该目录；工程内仍保留私有配置、身份锁、运行JSON及日志／报告。该目录在推理时持续使用，不能将它当作安装后可删除的临时下载目录。

首次网络下载量按锁定清单估算，GB为十进制：

| 入口 | 权重及配套数据 | 引擎／源码／依赖 | 首次下载合计 |
|---|---:|---:|---:|
| `Install-Strata.cmd` | IQ3_XXS两分片75.840GB＋约5GB MTP | 约0.7GB归档及小型依赖 | 约82GB |
| `Install-Strata-DeepSeek.cmd` | 主干138.239GB＋Engram110.595GB＋DSpark7.977GB＋元数据约5.8MB | 约0.46GB归档及小型依赖 | 约257～258GB |
| 两款合计 | 约338GB | 同目录源码／依赖可复用 | 按约340GB规划 |

网络下载量不等于最终磁盘占用：解压的运行库、pack／MTP派生文件和保留的旧准备批次会额外占空间。首次两款建议至少400GB可用，保留450～500GB更便于重复准备；原Ollama模型、备份及其他文件另计。MTP只读取固定原始检查点中所需的张量范围，不下载整套BF16检查点。

例如选择`E:\AIModels\AiServer-Strata`。先打开PowerShell进入实际AiServer工程根目录，保持停服，依次执行：

```powershell
.\Install-Strata.cmd --storage-root "E:\AIModels\AiServer-Strata"
.\Install-Strata-DeepSeek.cmd --storage-root "E:\AIModels\AiServer-Strata"
```

两个入口各自使用管理器记住的5080本机Python和服务配置，不使用开发机路径。也可给两款指定不同的绝对目录。准备成功后各自在推理配置保存`StorageRoot`；以后双击原CMD会沿用本款保存的路径。首次准备失败尚未发布配置时，重试需再次带同一个`--storage-root`才能续传该目录的文件。

指定目录结构如下，两款可以共用同一个根目录：

```text
E:\AIModels\AiServer-Strata\
  downloads\                       固定引擎／源码归档和断点文件
  models\IQ3_XXS\                  Qwen两个分片及其断点文件
  models\deepseek41\IQ2_XXS\       DeepSeek七个数据文件及其断点文件
  mtp-source\                      Qwen原始MTP张量
  prepared\<批次>\                 各次pack和MTP运行数据
  runtime\v0.2.9\                  引擎、源码和隔离依赖
  pip-cache\                       Python依赖下载缓存
```

0.11.0及更早版本已经下载的文件不会自动搬迁。需复用时，在停服且安装器已退出的状态，将原工程`.local\strata\downloads`、`models`、`mtp-source`中已有的内容复制到新根目录的同名子目录，再带`--storage-root`运行准备；完成文件会校验复用，`.download`会续传。原`.local\apps\strata`可保留，新目录会从校验后的归档解压运行库。原`prepared`不必复制，准备会生成指向新位置的新pack；成功发布新配置前保留原数据，失败可继续使用原配置。不要直接修改身份锁或在配置发布后只搬权重。

`--source-models`依旧只是已有完成GGUF文件的校验复制来源，不改变运行目录，也不复用`.download`；指定目标硬盘请使用`--storage-root`。未指定且没有已保存路径时，仍使用旧版工程内默认目录。上下文默认值保持下节设置，本补丁没有自动改为128K。

## 0.11.0 Strata双模型

在5080停服并备份后，将0.11.0更新包的`payload`合并覆盖到当前工程根目录。工程可以继续位于`D:\mhy\AiServer\AiServer-0.2.0-be0e34e`等既有位置；入口按自身目录定位，不依赖开发机路径。保留私有配置、`.local`、原Ollama模型、账号／key和数据库。

一次服务只启动一款Strata模型，停服后选择另一款。Qwen和DeepSeek各自保存推理配置、服务配置、身份锁、引擎及派生pack；DeepSeek准备入口不改写原Qwen配置。两款使用同一个AiServer API和认证，OpenCode／C#客户端从当前models清单选择，不直接连接本机引擎端口。

| 项目 | Qwen3.8 Flash-Next | DeepSeek V4.1 Flash 1017 |
|---|---|---|
| 安装入口 | `Install-Strata.cmd` | `Install-Strata-DeepSeek.cmd` |
| 量化 | 完整专家IQ3_XXS | ISTA-DASLab IQ2_XXS，2.00 bpw |
| 模型ID | `qwen3.8-flash-next:iq3_xxs` | `deepseek-v4.1-flash-1017:iq2_xxs` |
| 首次窗口／最大输出／预留 | 131072／16384／512 | 32768／16384／512 |
| 普通／thinking | none／high | none／high（上游75） |
| 初版路由与草稿 | 原完整模型，MTP启用 | 显式6专家，DSpark auto；auto可能判断不加载草稿 |
| 服务配置 | `config/server.strata.local.json` | `config/server.strata.deepseek.local.json` |
| 推理配置 | `config/inference.strata.local.json` | `config/inference.strata.deepseek.local.json` |
| 身份锁 | `config/models/strata.local.json` | `config/models/strata.deepseek.local.json` |

首次准备两款建议至少保留400GB可用SSD空间，已有其他模型和旧准备批次另计。DeepSeek固定下载四个主干分片、配套Engram、约8GB DSpark及一个小型元数据分片，合计256,816,878,701字节（约256.8GB），无需下载510GB原始检查点。Qwen下载及资源说明见下节。权重从固定HF revision下载，SHA256与上游准备清单核对；DeepSeek使用单独的0.1.55 Windows CUDA 13 `strata-dsv41.exe`。Python依赖按摘要版本隔离，共同依赖可复用。

1. 重新打开管理器，确认保存的是5080本机Python绝对路径和原服务配置。等待任务结束并停服、备份数据库后关闭服务；准备期间保持停服。
2. 双击`Install-Strata.cmd`准备Qwen。已有下载会校验复用；已成功准备且无需调整Qwen时可直接进行下一步。
3. 双击`Install-Strata-DeepSeek.cmd`准备DeepSeek。先检查源归档、隔离依赖及原生引擎，再下载七个固定数据文件；每5秒显示下载百分比／GB数／速度，完成文件会重新核对SHA256。超大文件的摘要计算也需时间。
4. DeepSeek使用上游专用pack配方，显式指定主干／Engram／元数据／DSpark及热专家profile，不复制另一份完整权重。检查pack完整性、固定DSML模板，并加载模型回答“法国首都”短问题；通过后才备份发布四份私有配置。失败保留原可用配置和下载，新批次pack单独保存。
5. 两款准备完成后，保持AiServer停止，双击`Test-StrataModels.cmd`。它按Qwen、DeepSeek顺序加载／关闭，测试普通／thinking、原生工具与多轮结果关联、取消恢复和恢复后再次生成，并执行同一C#生成样例。任一模型失败则汇总为FAIL，不把缺失模型跳过算成功。
6. 报告在`.local/strata/validation/<批次>/qwen.json`、`deepseek.json`和`summary.json`。包含各自窗口、6专家／草稿配置、加载时间、首片段耗时、usage、端到端输出速率及主机资源快照；快照不是峰值，C#样例未编译，不代表代码质量验收。两款窗口不同，比较时保留该差异。
7. 管理器选择“Strata Qwen”或“Strata DeepSeek”，运行“启动前检查”后启动。DeepSeek冷加载允许3600秒，Qwen默认900秒；等待就绪后再连接客户端。切换前等待任务结束并停服；开机任务如需切换，另行显式修改其服务JSON路径，管理器不会改写既有计划任务。

命令行入口（实际工程／Python不同时替换成5080自己的绝对路径）：

```powershell
& 'C:\ProgramData\anaconda3\envs\trt_test_1013\python.exe' '.\scripts\inference\Install-Strata.py' --family deepseek --server-config '.\config\server.local.json' --install-dependencies
& 'C:\ProgramData\anaconda3\envs\trt_test_1013\python.exe' '.\scripts\validation\Test-Strata.py' --all --benchmark
# 先停服，再显式尝试更大DeepSeek窗口；不自动降窗
& 'C:\ProgramData\anaconda3\envs\trt_test_1013\python.exe' '.\scripts\inference\Install-Strata.py' --family deepseek --install-dependencies --context 131072
# 需要先以8K排查时，同时显式指定较小输出预算
& 'C:\ProgramData\anaconda3\envs\trt_test_1013\python.exe' '.\scripts\inference\Install-Strata.py' --family deepseek --install-dependencies --context 8192 --max-output 2048
```

已有配置调优默认保留，窗口／输出只由显式参数调整。DeepSeek默认6专家用于保留原始路由数量，不自动选择上游5专家Faster模式；量化本身仍有精度损失。初版关闭DeepSeek磁盘会话槽持久化／自动pin，模型专家的SSD与内存缓存照常使用。启动原生日志放在对应`.local/strata/install/<准备批次>/engine-native.log`，其他准备日志亦在该批次下。

真实OpenCode文件工具测试在执行端进行：更新执行端的接入／验证脚本并保留该机密钥；服务器选择Qwen时运行`Check-ModelTools.py --models strata --thinking both`，停服切换DeepSeek后再运行`--models deepseek --thinking both`。两轮分别保存报告，不能在只发布一款模型的服务上同时请求两个别名。C#客户端通信契约不变，写死模型ID的配置需选择新ID。

回退：停服后选择原Qwen服务JSON或Ollama服务JSON启动，保留所有私有配置和数据库。0.11.0未增加数据库迁移。安装预检、本机合成回归及真实模型／5080容量和代码效果分别记录，当前交付边界见项目进度。

## 0.10.0 Strata初版

首次安装使用0.10.2或以上程序包。0.10.0准备入口若报`'InstanceLock' object does not support the context manager protocol`，发生在下载前；0.10.1已修复安装／验收入口的实例锁用法。

旧包若在`Preparing source`后报上游`bench/results/...json.gz`不存在，可能是工程目录叠加临时路径超过传统Windows路径限制。0.10.2只解压锁定清单中的运行源码／准备工具／许可与GGUF工具，跳过上游测试报告，并为ZIP／TAR解压、摘要检查和复用使用Windows扩展路径及较短的临时目录。保持停服，合并覆盖修复包payload，保留私有配置及`.local`后重跑`Install-Strata.cmd`；已通过校验的源码归档会复用，原`source.extract-*`失败临时目录不会参与新一轮准备，无需先清理或移动工程。

每次启动选择一种后端。原Ollama私有配置继续保留，Strata使用独立的`server.strata.local.json`、`inference.strata.local.json`和`models/strata.local.json`。两种后端共享原数据目录时沿用账号、API key与历史任务，不增加数据库迁移。

首次准备：

1. 从原管理器等待已有任务结束后停服，备份所选服务配置和数据库。合并更新包的payload到工程根，保留原私有配置与运行数据。
2. 检查64位Windows、NVIDIA驱动及空间。固定CUDA 13引擎的上游最低驱动为580.65；两个IQ3_XXS分片约70.6GiB，另需MTP、运行库、准备文件与余量。为首次准备至少留100GiB可用SSD空间；已有Ollama模型占用另计。64G内存与16G显存的实际缓存、速度及128K容量仍由本机验收确认。
3. 双击`Install-Strata.cmd`。默认使用管理器记住的绝对Python和原服务JSON；首次缺省窗口131072、输出16384、预留512，启用MTP、单生成位、文字／工具。准备工具固定Strata v0.2.9、0.1.55 Windows CUDA 13引擎、GGUF工具及模型revision／SHA256；依赖安装到忽略目录中的独立版本目录，不升级全局环境。过程可能较长，日志和报告在`.local/strata/install/`。
4. 下载允许断点续传，重试入口会复用通过SHA256校验的文件；不会接受摘要不符的完成文件。完整大小但摘要不符的`.download`须明确删除该文件后重试。已经解包的运行库也会重新核对内容，发现修改时停止并保留证据。已下载的两个原始分片可通过`--source-models`指向目录复用；复制前仍验证摘要。
5. 准备工具先加载真实模型并做一次短生成，通过后才备份／写入四份Strata配置；失败保留Ollama配置和原Strata配置，保留已下载数据供重试。派生pack与MTP运行文件存于`.local/strata/prepared/<批次>/`，旧批次保留用于回退；重复准备需为新批次另留空间。安装不会启动AiServer、修改管理器选择或自动更新5080。
6. 管理器选择“Strata配置”，运行启动检查后启动。引擎仅监听`127.0.0.1:18081`，AiServer仍使用原API端口与认证；冷加载允许900秒。OpenCode继续连接AiServer，刷新模型清单后选`qwen3.8-flash-next:iq3_xxs`，normal／thinking分别对应上游none／high。公开手工配置见`contracts/examples/opencode.strata.example.json`。

目标机最低验收入口（先停AiServer，不使用账号或key）：

```powershell
& 'C:\ProgramData\anaconda3\envs\trt_test_1013\python.exe' '.\scripts\validation\Test-Strata.py'
# 显式执行接近窗口的合成长输入；耗时与占用由目标机实测
& 'C:\ProgramData\anaconda3\envs\trt_test_1013\python.exe' '.\scripts\validation\Test-Strata.py' --long-context
```

报告在`.local/strata/validation/`，包含加载时间、普通／thinking、停止与恢复后再次生成、usage、耗时和资源采样。通过短检查不代表128K、16K完整输出或代码质量通过。随后重启AiServer，沿用OpenCode文件工具检查入口，显式选择`--models strata`；具体客户端步骤见本文件“本机OpenCode执行端”。

上下文和正文／思考共用窗口，思考与正文共用最大输出16384。初版采用保守容量估算，models接口明确标为估算；上游`fit_max_tokens=false`，超过实际容量明确报错，不自动缩减输出或截断输入。停止后必须确认唯一生成位和队列空闲，或终止并重启本工程拥有的进程树后才继续接单。

128K失败时保留报告，停服后显式重跑准备入口，例如：


切回Ollama：等待任务结束并停服，在管理器选择原Ollama服务JSON后启动。原配置与模型未被安装器改写；需要退回旧程序时使用`v0.9.12`对应程序包和原配置，保留账号／key／数据库，不删除Strata运行文件。所有切换均在服务停止后进行。

## 27B更新为80K

2026-11-02：27B默认总窗口调整为81920（80K），保留16384输出和512预留时，默认输入为65024；9B仍为128K。

1. 在5080从原管理器停服，备份原程序、所选私有配置和数据库；将本次更新包payload合并覆盖到工程根目录，保留该机私有配置、模型和账号/key。
2. 保持停服，双击工程根目录 `Set-Qwen38-80K.cmd`。入口使用管理器记住的Python和服务JSON，只定位实际注册的27B，先生成before-context备份再把NumCtx设为81920；输出预算、9B、其他注册模型、KV/FA/batch及身份锁保留。重复运行不会重复写入。
3. 从原管理器启动AiServer。保持RequireFullGpu=true；80K完整窗口和显存能否加载由目标机实际检查，不自动降窗或关闭全GPU要求。若失败，停服后仅从本次before-context备份恢复该27B配置，再重新启动。
4. 客户端重新读取模型能力，确认27B的contextTokens/defaultMaxInputTokens/maxOutputTokens为81920/65024/16384（输出或预留被自定义时以实际值计算）。IMVision插件DLL属于执行端，按插件交付更新，不复制到5080服务工程。

上述入口不下载模型、不启动推理、不修改服务注册和凭据；程序包准备与配置迁移通过不代表5080已实际应用或80K显存验证通过。

## 5080上下文容量实测

0.9.9提供`Tune-ModelContexts.cmd`。目标是充分使用当前5080可用显存，按每个模型的实际边界设置窗口，输出统一16384。最终窗口的长输入测试GPU总显存采样峰值不超过物理显存95%，保留约5%余量，桌面及其他程序占用也计入。公开默认窗口保持不变；只有目标机实测完成才修改其私有配置。测试固定当前权重、KV类型、Flash Attention、batch及单生成位，不更换量化、不下载模型、不开放CPU卸载。

1. 先从原管理器停止AiServer，退出占用模型库的托盘Ollama及其他模型测试器；保留该机原配置、模型与身份锁。覆盖本次完整更新包的payload，关闭其他占用GPU的程序，保持正式使用时的桌面／驱动环境。两个模型须已准备并实际注册。

3. 搜索上界为9B／Qwen3.8来源锁的262144。先做完整窗口全GPU加载和短生成，以二分法寻找1K（1024 token）精度的最大通过窗口，再搜索显存占用不超过95%的窗口。探索加载边界时可能暂时占满显存，最终写回值才要求保留余量。显存分配失败、CPU卸载、窗口缩小或超出共享GPU内存门限记为容量失败。网络、身份、计数器等其他故障停止测试，不拿来推断显存上限。
4. 对95%预算内的候选窗口至少两次重新启动临时引擎，用接近`窗口－16384－ReservedTokens`的合成原始文字进行prefill和最多256 token生成，按实际prompt_eval_count校准；支持thinking的模型逐次检查关闭／开启。短探针用于检查分配、长输入和生成阶段，既不证明完整16K输出稳定，也不证明长代码质量。若长输入失败或显存采样峰值超过95%，继续搜索较小的可复核窗口。95%按GPU总显存占用计算，包含权重、KV、计算缓冲与桌面占用；运行时其他GPU程序、驱动变化仍可能改变可用容量。
5. 只有全部所选模型完成，才逐份备份到`*.before-capacity-*.bak`，写回NumCtx、NumPredict=16384、存在的MaxOutputTokens=16384及RequireFullGpu=true，服务JSON、身份锁与其他私有字段保留。写入前检测并发修改；失败时只回退本次已写且未被其他操作修改的文件。取消或测试失败不提交部分窗口。
6. 从原管理器启动服务，再重启执行端`OpenCode-AiServer.cmd`刷新能力。核对models的contextTokens、maxOutputTokens和defaultMaxInputTokens；后者应为实测窗口减16384再减该模型ReservedTokens。手工配置者同步context／input／output。GPU容量并非代码质量验收，后续仍用真实业务题检查长上下文效果。

测试持续时间取决于窗口、加载和长输入吞吐，可能较长；控制台逐候选输出结果和显存采样峰值。报告为`.local/context-capacity/<本次目录>/summary.json`，包含每次通过／失败、已选窗口、最大加载窗口、95%显存预算内窗口、硬件／共享GPU内存采样、原配置摘要和备份路径；子目录保留trial.json及engine.log。达到模型原生上界时报告`upper_bound_reached=true`，表示未在允许范围内找到更高失败点。它测得当前条件下的最大通过网格点，不声称精确到单token或长期稳定上限。

### API key只读连接检查

本工程入口已保存key时运行`OpenCode-AiServer.cmd --check`，会带key依次查询身份、模型和就绪状态并刷新配置，不提交生成任务。直接调用HTTP／SDK的接入方可在PowerShell中运行以下检查；通过掩码输入key，不把密钥写入命令历史或输出：

```powershell
$aiServerRoot = 'https://szzj.nat200.top'
$aiServerSecureKey = Read-Host 'AiServer API key（完整密钥，不加Bearer）' -AsSecureString
$aiServerPointer = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($aiServerSecureKey)
try {
    $aiServerHeaders = @{ Authorization = 'Bearer ' + [Runtime.InteropServices.Marshal]::PtrToStringBSTR($aiServerPointer) }
    Invoke-RestMethod -Method Get -Uri ($aiServerRoot + '/api/v1/auth/me') -Headers $aiServerHeaders -MaximumRedirection 0
    Invoke-RestMethod -Method Get -Uri ($aiServerRoot + '/v1/models') -Headers $aiServerHeaders -MaximumRedirection 0
} finally {
    [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($aiServerPointer)
    Remove-Variable aiServerHeaders, aiServerSecureKey -ErrorAction SilentlyContinue
}
```

身份返回预期账号、models返回实际模型才表示密钥与模型列表接入成功；这不代表模型推理或公网SSE已验收。401时核对完整key及账号／撤销／有效期，向管理员申请更换后重新设置；不要尝试旧login／logout接口。网络失败时保留本地会话。需要完整文件工具验收时，再用上面的`--verify`，该操作会实际请求模型。

### 本轮方案与边界

按用户角色测试9B与27B两个模型，默认`--thinking fallback`，每题独立目录与会话，默认不跑容量探针、不并发。普通模式先运行；只有普通模式完成但未通过，且失败不是服务／传输故障时，才对同题启动独立thinking重试。需要双模型简单双模式校准时显式使用`--profile calibration --thinking both`。

| 模型 | 默认普通模式 | 默认thinking用途 | 默认范围 |
|---|---|---|---:|
| Qwen3.5-9B | 简单＋中等阅读、实现 | 普通失败后的同题兜底 | easy／medium |
| Qwen3.8-27B | 中等＋困难阅读、实现 | 普通失败后的同题兜底 | medium／hard |

`--thinking off`只测普通模式；`--thinking on`只测所选9B／Qwen3.8的thinking；`--thinking both`对全部题做双模式对照；`--thinking fallback`执行默认兜底计划。普通／thinking使用相同题面，thinking默认简单／中等／困难单题预算为600／1800／3600秒，普通仍为180／600／1800秒；读取、工具续答及修正均显式沿用该模式。预检要求两种思考模型实际发布`thinking=true`，缺少能力会停止整轮，不降级成普通模式。

测试使用独立OpenCode配置，通过normal／thinking variant与显式think选项控制；转发器逐请求核对`think=false/true`，缺失或不符会在发送到模型前停止该题。报告分开显示请求模式、实际思考字符、首次／最终通过和成本；思考文本不参与C#代码提取与功能判定。支持原生工具的模型走本机OpenCode真实读写；无原生工具的模型仍由OpenCode生成文字答案，题目材料直接提供，唯一C#代码由测试器保存，报告标记为text-code，不计成工具执行。

每题先保存首次脚本并做.NET 8编译／功能检查；不通过时，最多提供一次检查反馈让模型修正，首次与最终结果分别保留。服务或传输首次报错则停止该题，保留请求现场，避免客户端SDK把同一失败反复重试。进入下一题前等待服务ready，首题前及独立题目间额外等待默认2秒；同一用户指令中的工具续答不加间隔。

题目均为纯计算的单文件Script.cs，输入阅读脚本约72／660／2061行，简单／中等／困难交付上限100／1000／3000行，没有最低行数；每题包含一次修正和编译检查。测试宿主在交付目录外，模型不能执行任意命令或委派。本轮执行版本为v4-roles；题面修正了简单阅读题中未使用的方差干扰描述。v3及更早目录不能续跑，历史数据保留，可用`--report-only`离线重建。预算耗尽分类为客户端整题预算，不归为服务传输故障；取消请求缺少最终usage时，报告标为不完整，不合计成完整成本。

0.9.4补充请求／任务关联、预检计数、生成结束原因、正文／思考长度、工具数与具体校验错误。失败也记录引擎最终token和阶段耗时；日志不保存提示、参数值或思考正文。已结束的无效工具响应先完成收尾，再返回协议错误，避免不必要的引擎恢复。9B用固定官方tokenizer计数引擎完整渲染提示；预载、计数和生成统一shift=false，并在同一引擎互斥范围内按目标KV／FA执行。

## 动态上下文与OpenCode压缩（0.9.1）

更新程序后直接重启AiServer即可使用动态输入预算，不重新下载模型或生成身份锁。旧私有推理JSON中的`MaxInputTokens`保留也不会继续限制输入；实际预算由`NumCtx`、本次有效输出预算和`ReservedTokens`计算。未指定输出预算时采用服务上限；显式输出超过上限直接拒绝，通过校验后冻结入队并使用同一值生成，精确定义见接口文档。

以9B的128K窗口、16K默认输出及512预留为例，默认输入上限为114176 tokens；请求1024输出时为129536，仅请求1输出时为130559。models接口的`maxInputTokens`表示最后一种可能的最大输入，`defaultMaxInputTokens`为默认输出预算下的输入上限；另返回`reservedTokens`与`inputBudgetPolicy=window-minus-output-v1`。完整输入始终包含系统提示、历史双方消息、工具定义和工具返回。字节、图片和消息数量限制继续生效。

重启本机`OpenCode-AiServer.cmd`会从models刷新能力，保留原加密key。`limit.input`统一使用`defaultMaxInputTokens`，旧服务未返回该字段时按窗口减默认输出和预留推导，并保留更小的服务上限；不再使用仅留1个输出token的理论上界。手工配置者同样同步`limit.context`／`limit.input`／`limit.output`；9B的128K示例为131072／114176／16384，并启用`compaction.auto=true`、`prune=true`及10000的压缩缓冲。历史选择、旧工具输出裁剪和摘要由OpenCode负责，AiServer保持`truncate=false`／`shift=false`。

同一映射问题影响所有模型，公开默认值统一见本文件开头的推荐配置表；已有部署以models实际配置为准，客户端不能单独扩容。

AiServer预检超限在OpenAI入口返回HTTP 400／`context_length_exceeded`，引擎推理阶段超限通过兼容错误帧告知客户端，供其压缩后重试；原生入口仍为422／`CONTEXT_TOO_LARGE`。一次不可缩减的新输入自身超过窗口时，压缩历史也不能让它装下。OpenCode 1.19.4可能在成功压缩继续后仍显示一次ContextOverflowError通知并保留非零CLI退出码；应同时核对后续摘要、恢复回答与会话状态，不能只凭该退出码断言推理未恢复。

真实模型服务统一请求全部GPU层，并在启动／恢复及生成前核对引擎报告的全GPU驻留和完整配置窗口；旧私有配置缺少或关闭`RequireFullGpu`也不会解除运行时要求。扩展输入预算不扩大`NumCtx`，不切换CPU卸载；Windows驱动共享内存、实际KV／FA及峰值按本文件上下文容量实测章节核对。

维护者可用本机OpenCode运行`scripts/validation/Check-OpenCodeCompaction.py`，或用`--opencode`指定其绝对路径。此工具使用独立客户端目录、临时库、合成API key和回环模拟推理，检查HTTP预检与流内引擎超限两条压缩恢复路径；不读取保存的key、不访问公网模型，不证明真实模型的摘要质量或5080容量。

## 运行监控与慢请求

日常使用“运行监控”页，控制台与服务控制页日志保留任务接收／开始／结束的简短摘要，详细业务日志位于data_directory/logs/service.log。日志和监控不记录请求材料、回答正文、密码或令牌。

- 活跃账号：近5分钟有认证访问，或仍有未完成任务；不是精确在线人数。生成与排队分别按账号去重，同一账号可能同时在两项中。认证活动从本次服务启动开始统计，不要求客户端增加心跳。
- 任务可按账号、状态、提交日期（本机时区，YYYY-MM-DD，结束日期含当天）及总耗时超过20秒筛选，每页50项。统计与分页使用同一筛选条件；成功平均值和P95仅计算成功任务，P95采用最近秩法。失败、取消分别计数。
- 总耗时从服务端收到HTTP请求至任务终态，等于接收准备＋排队＋执行。首段等待从收到请求到首次非空正文片段成功保存，包含准备和排队；模型加载、输入处理和生成耗时来自Ollama结束帧，单位换算为毫秒。首段等待与模型内部耗时可能重叠，不能全部相加。
- token/s＝实际输出token数÷引擎生成秒数，通常在正常收到引擎结束帧后才有值。取消、异常、旧任务缺失的指标显示“—”；已保存的首段时间不会因取消而丢失。历史回填任务没有原始接收时间时，总耗时只从入队起算，明细中明确标示。
- 先比较接收准备／排队／执行，再查看首段等待、模型加载、输入长度和生成速度。服务端总耗时不包含客户端渲染及完整网络传输；若它明显短于客户端等待，需继续核对SSE代理与客户端处理。20秒只是排查筛选线，不承诺所有回答20秒内完成。

CPU、物理内存和GPU数据为整台主机的实时值，不单独归因于本服务，也不保存资源历史。Windows计数器和nvidia-smi在后台采集，GPU命令超时1秒；工具缺失、权限不足或指标不支持时显示“暂不可用”，不影响推理，无新增Python依赖。

服务写入data_directory/monitor-state.json，带时间、PID、创建时间、程序路径和配置指纹。管理界面可只读查看同配置的控制台／计划任务服务，不接管其停止权；快照超过10秒、进程身份或配置不符时显示数据已过期，人数与资源改为未知。历史查询只读，不创建库、不触发迁移；旧服务升级前没有实时快照是正常情况。

## 启动失败诊断

先点“启动前检查”，看错误码与阶段。它检查JSON、路径、端口、数据锁、契约、只读库和推理资料，不启动模型、不迁移库或改配置。

| 错误码 | 处理 |
|---|---|
| DATA_DIRECTORY_IN_USE | 从原入口停止占锁操作，不删除instance.lock |
| API_PORT_IN_USE / ENGINE_PORT_IN_USE | 核实占用进程，停止旧API／模型；改端口须同步隧道 |
| ENGINE_EXECUTABLE_MISSING / STARTUP_FILE_MISSING | 检查inference_config、ExecutablePath、ModelsPath、契约和SQL迁移 |
| MODEL_IDENTITY_CHECK_FAILED | 核对实际版本、模型digest、量化、模板，不改锁绕过 |
| STORAGE_INIT_FAILED / STORAGE_SCHEMA_UNSUPPORTED | 核对权限、完整性和源码版本，保留原库与备份 |
| CONFIG_FIELDS_INVALID | 按报告字段名修复，不输出原值 |
| NATAPP_UNMANAGED_INSTANCE | 核实并从原入口停止手动连接器／独立任务 |

路径问题可能在JSON指向的推理文件中，不因统一失败提示替换整个私有配置，也不删除库／锁试错。

“Ollama程序文件检查通过”只表示文件存在，不是重复运行。真正的ENGINE_PORT_IN_USE会尽可能显示监听PID、程序路径及本工程进程记录是否匹配；模型子进程不会仅因同名而被判定冲突。检查托盘Ollama自启、旧Start-Ollama.py／控制台和独立开机任务，从原入口关闭已确认的外部实例。管理器不会按进程名批量结束Ollama，也不会接管未知进程。自有引擎暂停创建后先加入Job再恢复，失效PID记录自动移除。

## 数据、取消与备份

SQLite位于data_directory/jobs.db，WAL＋FULL。默认每账号2项未完成、全局10项、单生成位；每分钟请求120次／提交6次。新任务终态起正文保留1天，幂等30天，旧任务保留原到期时间。独立task_performance表的账号／状态／时间／token和引擎耗时保留7天，不依赖正文或幂等记录的清理；不延长正文保存。到期正文立即不可读、指标立即从查询隐藏，启动／每小时分批物理清理；备份另行管理保留。

日志仅追踪号、状态与事件，不记录认证头或业务正文。取消／断线保存停止意图后关闭推理并恢复引擎，恢复校验后才释放执行位；恢复失败拒绝新提交，历史可查。断线查原任务，新生成用新编号。

升级前停止服务，用管理界面“备份当前数据库”：标准库一致性备份包含WAL，不迁移schema或创建空库，输出到.local/backups。CLI也可用：

```powershell
& 'C:\ProgramData\anaconda3\envs\trt_test_1013\python.exe' '.\scripts\server\Manage.py' --config 'D:\github\AiServer\config\server.local.json' backup 'D:\github\AiServer\.local\backups\before-update.db'
```

restore仅恢复到全新数据目录并检查完整性，接受v1至v5备份；通过新配置启动，不覆盖在用库。cleanup手动清理；recovery-confirm仅作停服且核实旧模型已退出后的异常兜底。v1至v4升级v5会提前自动一致性备份，移除活动用户表的密码字段，保留旧用户、key、任务、片段及到期时间，并保留／回填仍可读取的历史时间和token指标。回退须使用升级前备份与旧程序。

## 公网与开机运行

当前Web入口https://szzj.nat200.top，NATAPP本地目标127.0.0.1:18080，平台开启域名HTTPS、本地HTTPS关闭，换域名同步allowed_hosts。只开放API，不转发模型端口／管理命令。

基础配置页填写public_base_url并保存、重启后，本机就绪时自动检查该HTTPS入口的/api/v1/health，此后每60秒检查，单次超时5秒，不携带业务令牌、不跟随重定向，校验TLS、HTTP状态和健康内容。地址只允许HTTPS来源，不含账号密码、路径、查询参数或片段。旧配置缺省为空，界面显示“未配置公网检查地址”，不影响本机启动；需要公网检查时填入该主机实际域名。

界面分别显示本机API、NATAPP进程及公网检查的结果／时间／延迟。成功显示“服务器自检可达”，失败显示HTTP、超时、网络或证书等原因；失败不重启模型或阻止本机运行，控制台仅在公网状态变化时提示。服务器自检不等于另一外网电脑成功连接，也不证明SSE及时透传。

Install-StartupTask.ps1用绝对Python／配置路径注册同一个Run.py，默认SYSTEM，拒绝覆盖已有同名任务；账户须可读Python／模型／INI、可写数据目录。已有正确任务无需改入口，停用独立Ollama／NATAPP任务。同一隧道token不在两台机器同时运行。

本机访问域名不能代替另一外网电脑验收；公网SSE／断线、5080和无人登录实际结果见项目进度。
