# 跨会话协作与文档维护

更新日期：2026-10-23

## 1. 文档职责

| 文件 | 维护者 | 内容 |
| --- | --- | --- |
| `README.md`、`docs/主方案.md` | 主会话 | 项目入口、总体需求、跨专项决策、最终架构 |
| `docs/项目进度.md` | 主会话 | 里程碑、专项状态、已完成验证和下一步 |
| `docs/实现线A-客户端服务端与公网.md` | A 实现会话 | A 的步骤、修改文件、证据、阻塞与交接 |
| `docs/实现线B-模型能力与推理.md` | B 实现会话 | B 的步骤、模型／配置版本、证据、阻塞与交接 |
| `docs/专项/NN-专项名.md` | 对应专项会话 | 方案比较、细节、证据、专项结论和交接摘要 |
| 代码、配置、实测报告 | 用户授权的实施会话 | 真实实现与实验依据；产生后由专项文档链接 |

专项会话可读取主方案和其他专项，默认只更新自己的专项文件。跨专项接口冲突、总体架构变化由主会话汇总协调。用户明确授权修改范围时按用户要求执行。

本轮按用户提出的双线方向组织实施：A／B 会话在启动指令授权范围内维护本线代码、线进度和涉及专项；原“单专项讨论默认只改专项文件”不限制已授权实施。公共项目文件和接口由单一维护者处理，归属见实施规划第 0、7 节。

用户已确认的结论应直接记录并同步，不因换会话而重复请求同一项确认。新的未决选择不能因为写进了文档就视为已确认。

## 2. 状态与证据规则

每项重要结论分别标识：

- 决策状态：未决／当前建议／用户已确认／已废弃。
- 验证状态：未验证／官方资料核实／实际测试通过／实际测试失败。
- 依据：用户说明、仓库文件与符号、官方链接或实际测试报告。

硬件计划、库支持列表、安装成功、实际 GPU 推理成功分别是不同事实。不得把推导步骤或计划中的测试写成已执行。

示例代码中的业务值不自动成为产品规范；待确认的索引、单位、复位、通信协议等必须保留为未知项。

## 3. 新专项会话启动提示

新会话应使用同一个工作目录 `D:\github\AiServer`。复制以下提示，替换专项编号和文件名：

```text
这是 AI C# 脚本助手项目的 S02「模型与推理部署」专项会话。
工作目录为 D:\github\AiServer。

请先读取：
1. AGENTS.md
2. README.md
3. docs/主方案.md
4. docs/项目进度.md
5. docs/跨会话协作.md
6. docs/专项/02-模型与推理部署.md

本会话先讨论并收敛该专项方案。读取已确认事实，聚焦本专项的目标和待决策问题；
重要技术选型核对官方资料。需要其他专项信息时按文档指针查阅。
持续更新本专项文件，区分当前建议、用户已确认和实际验证结果；
结束本轮时更新文末“回传主会话摘要”，便于主会话合并。
默认只修改本专项文档；代码实现和部署执行的范围按本会话用户后续指令确定。
```

S01～S06 的编号和路径见 [文档入口](../README.md)。用户自行选择何时创建专项会话；本次文档整理没有创建新会话。

## 4. 专项如何回传

每个专项文末保留同一格式：

```text
本次结论：
决策状态与用户确认依据：
已核实的资料／已执行的测试：
尚未验证和待决策事项：
对其他专项的影响：
建议主方案更新项（关联 D 编号）：
下一步：
```

每个事实的细节只维护在负责的专项。摘要写结论和文件指针，不复制整段会话或其他专项内容。

## 5. 主会话如何汇总

专项文件更新后，可在主会话发送：

```text
请读取已更新的 docs/专项/02-模型与推理部署.md，
根据文末摘要汇总到 docs/主方案.md 和 docs/项目进度.md。
保留已确认、建议和未验证之间的区别；标明跨专项影响和下一步。
```

主会话读取文件中的实际内容，核对确认依据，更新相关 D 决策、阶段进度和依赖。已有明确用户确认不再重复询问；没有确认的选项继续标记建议或待决策。

## 6. 避免并发覆盖

- 同一专项文件由一个活动专项会话负责；同时讨论不同备选方案时，可先在该文件建立 A／B／C 小节。
- 如果某个备选方案需要大量细节，再由该专项拆成子文档，并在专项入口中链接；尚未展开的选项不提前创建空文件。
- 各会话写文件前重读相关内容，合并其他会话的有效修改。
- 主方案与进度集中由主会话维护，减少多个会话同时修改同一文件。
- 本项目采用文件交接。会话间发送消息、创建新会话等操作按用户的明确指令开展。

## 7. 从讨论进入实施

01～05 初步收敛后，读取 [实施规划](实施规划.md) 和 [S06](专项/06-联调与验收.md)。实施以 P 工作包和 G 验收门槛组织，不按专项编号一次性做完，也不把每个专项建成独立程序。公共契约与目录归属以实施规划为准。

默认只开两个实现会话，分别使用 [A 线](实现线A-客户端服务端与公网.md)、[B 线](实现线B-模型能力与推理.md) 文末启动提示。下面的 P0 模板仍可用于只实现一小步，不要求另开第三个会话。

用户准备开始实现时，可在对应会话使用以下提示，替换工作包和范围：

```text
请在 D:\github\AiServer 实施 P0「业务契约与最小样例」。
先读取 AGENTS.md、README.md、主方案、项目进度、实施规划、S06，以及 S01／S02／S04／S05。
范围：依据 S04 v0.4 落实图文兼容 v1 的 schema 和请求／响应样例，准备少量可重复输入。
保持文档中用户已确认的图文与完整脚本边界；预算未知时明确拒绝，不伪造已校准算法。
本工作包不安装模型、不购买公网、不实现完整宿主 UI。
完成后检查契约和样例一致性，更新负责专项的真实结果与 G0 证据，交由主会话汇总。
```

其他工作包按同样方式写明拟改文件、必要配合与实际验证；代码实施范围来自用户发送的实施指令，不因存在模板就视为任务已创建或已获部署授权。

## 8. 每小步回写，主会话汇总

1. A／B 每完成一小步，先更新本线进度表：交付版本、实际文件、已测结果与证据、未测／阻塞、接口影响、下一步。
2. 技术细节回写对应专项的原位置，不在进度表重复整份方案；模型、配置和测试期望变化保留版本关联。
3. 改变公共字段、内部接口、图片处理／预算或停止行为时，在交接中明确需要另一线配合；先更新唯一契约／样例再调整消费者。
4. 主会话汇总时重新读取两线文档与实际证据，更新主方案、总进度、下一集成点。单凭“已完成”文字不足以标记验收通过。
5. 正常调参、修复和步骤细化由已授权实现会话继续推进，不要求每个默认值重新审批；新的跨线冲突和产品范围变化交主会话协调。

两线先共享最小边界，再独立测试；最小真实实现可用时就进行接通检查，之后继续各自优化，最终用 S06 完整联调。全过程采用文件和证据交接，不依赖自动跨会话转发。
