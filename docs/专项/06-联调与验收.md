## 2. 验证层次必须分开

| 层次 | 能证明什么 | 不能替代什么 |
| --- | --- | --- |
| 文档／配置静态检查 | 链接、JSON／schema、脚本语法与配置一致 | 应用、GPU、网络和业务结果 |
| Fake＋真实 API／SQLite | 认证、归属、幂等、状态、重启与恢复 | 真实视觉、模型质量与 GPU 停止 |
| 独立真实模型 | 图片确实输入、模型理解、资源和内部调用 | 业务队列、外网与宿主正确 |
| 外网＋Fake | HTTPS、上传、转发、查询和重连 | 模型质量、真实设备行为 |
| API＋VL＋Demo | 图文映射、联合预算、结果和取消闭环 | IMV 真实编译及业务验收 |
| 真实宿主＋明确预期 | 接口、编译、业务结果、显式应用与恢复 | 未测设备、未覆盖工程与长期在线保证 |

原型小样例、完整脚本任务和正式交付分别判定。4K／1024 容量不足必须记录，不以截输入、只回方法或 diff 判为完整交付。

## 4. 模型与业务核心用例

准备材料时登记固定 caseId、预期与发布阻断级别，不凭模型自评判结果。

| 编号 | 场景 | 必须观察 |
| --- | --- | --- |
| V01 | 标准库短代码、空／边界输入 | 需求符合、输出未截断；编译仅在实际执行后记录 |
| V02 | 顺序、分支、汇合、回路的小图 | 分别核对节点、有向边、条件；不按位置猜顺序 |
| V03 | 同文字但改变关键箭头的对照图 | 回答随实际图改变，固定文本回答不能算视觉通过 |
| V04 | 模糊连线、隐藏条件、复位责任 | 对关键缺口说明未知或澄清，不编造 |
| V05 | 目录／截图 ID 冲突或旧版本 | 不以截图覆盖真实 ID／类型，指出关联缺口 |
| V06 | 真实 SDK 的计算与集合任务 | 绑定、单位、公式、索引、边界正确，返回完整脚本 |
| V07 | 通信、拍照计数和跨产品周期 | 请求／完成、通知／复位区分；模拟和设备分别判定 |
| V08 | 修改已有脚本 | 完整结构和辅助代码，满足变更且检查原关键行为回归 |
| V09 | 澄清后新一轮 | 显式保留选择与来源；parentJobId 不当作隐式历史 |
| V10 | 真实编译诊断反馈 | 原需求＋候选代码＋诊断可复现，修复后检查业务回归 |
| V11 | 长原脚本＋SDK＋目录＋图片 | 无静默裁剪、输出完整；拒绝与截断分别统计 |
| V12 | 生成后编辑脚本，再主动应用 | 未主动应用不覆盖；旧结果不无提示覆盖新稿，可恢复 |

S01 建议 12～20 个任务、S02 建议约 20 张代表图，都是起步规模，不是已有资产或统计充分性保证。首个 smoke 用少量已知图与短代码；随后扩充真实任务，保留未提供完整参考答案的 holdout。

比较顺序：同模型资料／示例对照→真实诊断的有界反馈（可先比较 0／1／2 次修复）→同图同预算的 4B／8B→确有失败证据时再比较视觉拆分或受控 Agent。修复次数是实验组，不是已选产品规则。

## 5. 图文、上传与恢复专项

### 5.1 图片和联合预算

- 测空图、单图、原字节／像素／长边／正文边界、坏 Base64、伪 PNG、损坏图；错误时不调用模型。
- 核对实际图片 hash、顺序、来源修订、处理策略及原生 images，不把 Base64 拼进普通文本。
- 文本、视觉、模板和输出共同计入 profile；预算未知不能宣称普通图文就绪。返回 token 数不能单独证明发送前约束正确。
- 保守上界要有锁定模板／处理范围证据；外部分词或 processor 同样需核对与 Ollama 的一致性。不能回退旧 Qwen2 算法掩盖缺口。

### 5.2 公网与上传

- 核对实际 NATAPP 入口限制；本地接受 5MiB 不代表公网必然接受。
- 分开记录上传、接收／校验／入库、排队、模型加载／生成和下载；120 秒提交、15 秒查询是默认建议，不与 600 秒执行混用。
- 丢提交响应时原 clientRequestId 查回；同键改图冲突；断线不隐式取消已接受任务。
- 5 用户约 3 秒活动轮询，复用连接、退避；记录实际连接与流量，不反复下载结果或原图。

### 5.3 停止、故障与托管

- 完成、主动停止、超时分开；停止后晚到正文不覆盖下一轮。
- Fake 竞争测试使用可控屏障；真实取消必须从已开始的推理触发。
- 任务终态与执行位 draining／recovering 分开，正常经验证路径自动收尾，异常才人工恢复。
- 分别停止／恢复 API、模型、隧道；测写入失败、崩溃残留与身份变动，查询旧结果和接新任务分开。
- 改模型、模板、图片处理或硬件后重验相关预算、取消和代表任务，不无理由重复无关测试。

## 6. 通过条件和限制

- 确定性的认证归属、幂等、竞争、终态、持久恢复关键用例必须满足断言，失败不能以模型效果好抵消。
- 研发原型的真实图片和短代码闭环只是继续评估依据，不能升级为总体可靠性结论。
- 完整项目的关键业务任务必须在最终 profile 满足预期、完整交付与真实检查。业务负责人提供的关键清单与其他质量目标在 P4 实测前登记；缺业务预期、SDK 或编译器时该层阻塞，不凭空承诺通用成功率百分比。
- 分别报告完整交付、视觉、绑定、真实编译、业务、澄清、修复回归、预算拒绝、耗时和排队；围栏闭合／模型自评／编译通过不能替代业务正确。
- 当前没有速度 SLA，先记录各机器的实测分布和极端值，再形成产品目标。4GB CPU 分担不冒充 5080 性能失败，8B 也不预设合格。

## 7. 测试资产与报告

目录按实施规划：`tests/AiServer.Tests/` 放确定性自动化，`eval/cases/`／`eval/holdout/` 放能力任务，`knowledge/examples/` 放参考资料；不把测试答案默认送给该题模型。

每个 case 最少有：caseId、需求、输入文件、上下文／截图来源、预期、允许未知、所需验证层及候选 profile／prompt。报告记录实际版本，测试配置不能越权覆盖服务参数。

每份报告记录：

1. 日期、机器／网络、代码／引擎版本、模型 digest、模板／预算／图片策略和 prompt 版本。
2. caseId 或 T／A／N 编号、实际步骤、预期、实际结果及证据位置。
3. 通过／失败／阻塞／未执行，限制与原因；重复运行保留全部结果，不挑最好一次。
4. 冷热、排队、上传、执行计时及峰值资源，测量方法与 CPU 分担情况。
5. 原始私有证据放 `.local/reports/` 或受控位置，`docs/验证记录/` 放脱敏摘要；不记录凭据和图片 Base64。

建议按 G 编号命名报告；报告文件在实际执行时创建，不能以文件名或空报告标为通过。
